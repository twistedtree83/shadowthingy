# G5 — Image, EXIF, and metadata integrity flags

Issue: #6 · Branch: `sprint/gnomon-mvp` · Status: **shipped**

## What shipped

`Gnomon.meta` — EXIF interpretation, the three integrity detections, timezone
recovery, and a sensor-width table for G7's Tier 2. Plus the shell: drag-drop
(and click-to-browse), orientation handling, prefill of the solar inputs, and
the flags rendered in the result region.

24 headless assertions. Browser-verified against five generated fixtures.

## The fixture pipeline is new, and G6/G7 should use it

`scripts2/fixture-scene.js` emits a synthetic scene as JSON;
`scripts2/make-fixture.py` draws it into five JPEGs under `samples/`
(gitignored — the repo never holds imagery, which is the whole point of the
app). See `scripts2/README.md`.

Two properties make it worth more than a photograph off a phone:

- **The geometry comes from `Gnomon.synth`.** Python is a pencil; nothing in the
  fixture pipeline reimplements a projection, because a second implementation is
  exactly what would let a fixture agree with a bug.
- **The sun angles come from `Gnomon.solar` at the instant the EXIF claims.**
  So the shadows genuinely match the stated time and place, and G13's Verify
  mode has something real to agree with. They were hand-picked at first and that
  was wrong — the engine says 56.42°/278.30° for Sydney at 15:20 AEDT, not the
  48.6°/292.4° I had guessed.

## Five real bugs, all found by pointing the real library at a real JPEG

None of these throws. Each produces an image that opens, EXIF that parses, and a
value that is quietly absent or wrong.

1. **`Orientation` arrives as prose.** exifr revives it to `"Rotate 90 CW"`, not
   `6`. `Number("Rotate 90 CW")` is `NaN`, which fell back to "no rotation" and
   would have left every vertical in the image lying on its side — with nothing
   downstream able to detect it, because the geometry is perfectly
   self-consistent in a rotated frame.

2. **`DateTimeOriginal` arrives as a `Date`.** The regex path failed on it
   entirely, silently losing the capture time on every real photograph. The
   parser now duck-types on `getFullYear`. Reading a Date's components is
   clock-free — the core still constructs none of its own.

3. **The 35mm focal length is `FocalLengthIn35mmFormat` in exifr**, not
   `FocalLengthIn35mmFilm` as the EXIF spec names it. Reading only the spec
   name meant Tier 1 would never fire and every photograph would silently drop
   to a weaker calibration and a wider band. Both names are accepted.

4. **The CDN path was wrong.** `full.umd.min.js` does not exist in the package;
   it is `full.umd.js`. The script tag failed silently and `window.exifr` was
   simply undefined, which the loader treats as "no metadata" — so every image
   would have looked stripped.

5. **A rotated photograph looked cropped.** The worst of the five. EXIF
   dimensions describe the *stored* bytes; decoded dimensions are *after*
   orientation is applied. For orientations 5–8 those differ by an axis swap on
   an image that has been neither cropped nor resized — so the naive comparison
   reported both, and a spurious crop flag permanently discredits the principal
   point and widens every downstream band for no reason. `analyse` now swaps the
   recorded dimensions before comparing, and there is a test asserting a rotated
   image raises no flags **and** one asserting a rotated-and-genuinely-cropped
   image still does, so the fix cannot become a blanket excuse.

## Decisions taken

- **`createImageBitmap` already applies EXIF orientation, so the app must not.**
  The spec's opt-out (`imageOrientation: "none"`) was dropped and silently falls
  back to `"from-image"` — both modes returned identically-oriented bitmaps in
  Chromium. Re-applying would rotate twice. Where the orientation swaps axes
  this is *checked* rather than assumed: if the bitmap still matches the stored
  dimensions the decoder skipped it and the app applies it. For the mirror and
  180° cases the dimensions are identical either way, so there is nothing to
  check and the modern behaviour is assumed. The debug panel records which of
  the two happened.

- **Timezone is never defaulted to UTC.** `OffsetTimeOriginal`, else GPS
  differenced against local time, else `null` and a loud flag. It is the single
  field that most affects the answer, and a silent default would corrupt every
  result by exactly the offset.

- **GPS differencing rounds to the nearest quarter hour** and rejects anything
  outside [−12, +14]. Camera clocks drift by seconds; real offsets are
  quarter-hour multiples. A result outside the range means the two timestamps
  are not describing the same instant, so it claims nothing.

- **Latitude 0 is a real coordinate.** Testing truthiness on GPS values would
  silently discard Null Island, which is both a genuine location and a common
  EXIF bug pattern worth seeing rather than hiding.

- **The sensor table is deliberately small.** A wrong entry is worse than a
  missing one, because it produces a confident *mid-tier* answer rather than
  falling through to a visibly wide one.

## Environment note

**`cdn.jsdelivr.net` is blocked by this environment's egress policy** (HTTP 403
on CONNECT). That is an org policy denial, not an app fault — the app is correct
to load exifr from a CDN, and it degrades gracefully when the script is absent.
The browser tests route the CDN URL to a locally-fetched copy of the real
package (npm registry is permitted), so the real library is exercised through
the real code path.

Anyone running this where the CDN is reachable needs no such workaround.
