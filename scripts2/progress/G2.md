# G2 — Solar engine: NOAA position, six invariants, manual UI

Issue: #3 · Branch: `sprint/gnomon-mvp` · Status: **shipped**

## What shipped

`Gnomon.solar` — NOAA's solar position algorithm implemented directly, with
atmospheric refraction, solar noon, sunrise/sunset and the shadow multiplier.
All six invariants pass, in the headless suite **and** in the visible panel from
the same definitions.

A manual calculator in the readout panel takes latitude, longitude, date, time
and UTC offset and shows elevation, azimuth, shadow multiplier, declination,
equation of time, solar noon and sunrise/sunset, live.

Browser-verified. Sydney, 22 December 2023, 13:00 AEDT:

| | Gnomon |
|---|---|
| elevation | 79.472° |
| azimuth | 351.686° (north — southern hemisphere) |
| shadow multiplier | ×0.186 |
| solar noon | 12:53 |
| sunrise / sunset | 05:41 / 20:05 |

Those sunrise and sunset times are right to the minute for Sydney at the
solstice, which is the cross-check the gate asked for.

## Decisions taken

- **The hemisphere flip falls out of the formula, not out of a branch.** At
  solar noon `H = 0`, so the azimuth reduces to `atan2(0, tanδ·cosφ − sinφ)`.
  Negative x gives 180° in the north, positive x gives 0° in the south. There is
  no `if (latitude < 0)` anywhere in the engine — which is the point, because
  that branch is exactly where a hemisphere bug would live.

- **Geometric and apparent elevation are both returned.** Invariant 3
  (`90° − |φ − δ|`) is a statement about geometry, so it is asserted against
  `elevationTrue`. Folding refraction in first would let an error in either one
  hide behind the other. `elevation` is the apparent value and is what the app
  uses everywhere else.

- **The shadow multiplier is `Infinity` at or below the horizon**, not a large
  finite number. A vast finite multiplier reads like a measurement; `Infinity`
  reads like the refusal it is. The manual UI prints "no shadow".

- **Polar day and polar night are named, not NaN.** `cos H₀` leaves [−1, 1] at
  high latitudes and `Math.acos` would return NaN, which then propagates
  silently through every downstream subtraction. `sunTimes` returns
  `polar: "day" | "night"` with null times instead.

- **`dateFromDayOfYear` exists so the year-long equation-of-time sweep needs no
  `Date`.** The purity gate forbids `new Date` in the core, and rightly — but
  invariant 2 has to walk 365 days. A small leap-year-aware helper is the honest
  way to do that.

- **Solar noon takes one refinement pass.** The equation of time is evaluated at
  the estimated noon rather than at midnight. Worth about a second, and it
  matters because invariant 5 (symmetry about noon) is only as good as the noon
  it is symmetric about.

## Snags

**One test was wrong, not the engine.** The Nairobi crossover case asserted the
June noon sun appears *south*, reasoning that δ = +23.4° is north of the
equator. That is the wrong comparison: what decides the side is whether δ is
north or south of **the observer's latitude**. Nairobi is at 1.29° S, so
δ = +23.4° is north of it and the sun appears north; in December δ = −23.4° is
south of it and the sun appears south.

The engine had it right, and the elevations confirmed it independently —
65.27° = 90 − |−1.29 − 23.44| and 67.85° = 90 − |−1.29 + 23.44|. The test now
asserts the declination-versus-latitude relation explicitly rather than relying
on my reading of it.

Worth keeping the case: London and Sydney each stay on one side of the sun all
year, so a sign error that only appears when |δ| > |φ| would survive both.

## Gates added

- 14 headless solar assertions; 15 more in the panel. Total suite: 63 headless,
  24 in-panel, purity clean, network clean.
- Browser smoke test confirms no console errors, live recompute on input, and
  the debug toggle. The toggle correctly ignores backticks typed into a field —
  which initially looked like a broken toggle and was the guard working.

## Left for later slices

- The manual UI already warns below 5° elevation. **G14 turns that into a real
  guard**; here it is only a note, because the manual calculator is where a user
  first meets the low-sun regime.
- Timezone is a plain UTC offset. There is no timezone database and none is
  planned — G5 recovers the offset from EXIF instead.

## Note for whoever picks up G10

`solar.position({year, month, day, minutes, tzOffsetHours, latitude, longitude})`
is the whole interface for the inverse solve — it is pure, allocation-light, and
takes about 1.2 µs per call, so 500k grid cells is comfortably sub-second.

For a UTC-anchored sweep, pass `tzOffsetHours: 0` and `minutes` as UTC minutes;
the engine subtracts the offset before computing the Julian Day, so that is the
same instant everywhere and only `longitude` moves the hour angle.
