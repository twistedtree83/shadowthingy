# G6 — Marking: objects, loupe, and the three line families

Issue: #7 · Branch: `sprint/gnomon-mvp` · Status: **shipped**

## What shipped

Three-click object placement (base → top → shadow tip), draggable handles with a
5× loupe, undo, per-object delete, clear, and the three line families drawn in
distinct colours with dashed extensions running toward their convergence points.
Plus the two optional marks G7 and G8 need: a scene rectangle (Tier 3) and a
reference direction with a bearing input (azimuth against north).

`geom.extensionDirection` is the new pure piece, with 4 assertions. Total suite:
90 headless.

## The gate, verified end to end in the browser

Marks placed through the real UI on the fixture photograph, then compared
against the analytically-computed vanishing points:

| family | \|cos\| to truth | at infinity | condition |
|---|---|---|---|
| `v_z` | 1.000000000000 | false | 6.1e-10 |
| `v_shadow` | 1.000000000000 | false | 6.8e-9 |
| `v_sun` | 1.000000000000 | false | 7.4e-9 |

That is the full round trip — synthetic scene → JPEG → drag-drop → EXIF →
orientation → clicks → families → vanishing points — agreeing with ground truth
to twelve decimal places.

Dragging works, the loupe appears during a drag, and the handle lands where it
is dropped.

## Decisions taken

- **A finite vanishing point behind the segment still gets an extension drawn
  toward it.** The dashed line's job is to reach the convergence point; drawing
  it the other way would show lines that never meet and imply a disagreement
  that is not there. Only for a vanishing point *at infinity* — where both
  directions along the line reach it equally — is the tie broken by continuing
  the segment rather than doubling back.

- **The oriented image is kept in an offscreen canvas.** Marks are redrawn on
  every pointer move during a drag, and re-decoding the file each time would be
  unusable. A redraw is now one blit plus the overlay.

- **Hit-testing is in display pixels, not image pixels.** The grab radius should
  feel identical whether the image is shown at 1:1 or scaled to a third; testing
  in image space would make handles nearly ungrabbable on a large photograph.

- **Loading a new image clears every mark.** They were placed in the old frame's
  coordinate system and would be silently wrong in the new one — silently, which
  is the problem.

- **A zero-length segment makes `currentFamilies` report nothing** rather than
  letting `geom` throw into the render loop. G3 throws on these by design; the
  UI can produce them from a double-click, so the shell catches and reports no
  vanishing points rather than showing ones computed from fewer lines than the
  user marked.

- **Undo peels the half-placed object first.** That is the order a user expects,
  because the partial object is the thing they can see themselves in the middle
  of.

- **At exactly two objects the panel says so.** Two fixes each vanishing point
  exactly, so clicking error passes straight through with nothing to average
  against. The note appears only at two, which is where it is actionable, rather
  than as permanent chrome.

## Left for later slices

- `state.reference` and the bearing input are captured but nothing consumes them
  yet — G8 uses them to report azimuth against north.
- `state.rectangle` is captured and drawn but not yet fed to Tier 3 — G7.
- The marking canvas has no zoom or pan. On a large photograph the loupe
  compensates; if G17 finds that insufficient, pan/zoom is the fix.
- `window.gnomonOnMarksChanged` is the hook G7/G8 attach their recompute to.

## Note for whoever picks up G7

`Gnomon.synth.families(state.objects)` is the shared path from marks to
segments — the same call the synthetic round trip uses, so a fixture and a real
photograph travel identical code.

`currentFamilies()` in the shell returns `{z, shadow, sun}` vanishing points or
`null`. Tier 4 needs `v_z` and `v_shadow`; the residual in G8 needs all three.
